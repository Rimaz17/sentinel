# 0008, The detector is measured against the simulator's own outbreaks

Status: accepted · 2026-09-27

## Context

The project overview defines success by numbers: detection rate, time to
detect, and false alarms per week when nothing is happening, each at several
sensitivity levels. CLAUDE.md requires that any such number in the README come
from an actual run. Because the simulator decides when each outbreak starts, the
detector can be scored against ground truth. The question is how to run enough
outbreaks to mean something.

Running them through the full pipeline, posting every report to the API and
checking hourly against PostgreSQL, costs a nine-week backfill per outbreak, so
a few hundred outbreaks would take days.

## Decision

`python -m sentinel_detector evaluate` measures the detector at the level of
counts, in memory, in under a minute:

- **Same distributions.** Hourly counts are drawn from the simulator's own
  baselines, weekday and hour-of-day rhythm, Poisson sampling and outbreak
  model (`sentinel_simulator`), not from a copy of them.
- **Same rules.** Each hourly check's nine weekly windows go through the
  production `score` function, and false alarms are counted with the
  production episode rule. Only the storage layer is bypassed, and that is
  covered by the detector's integration tests.
- **Outbreaks.** 600 of them: every district and symptom group, at +50%, +100%
  and +200% of its usual weekly count at peak, each as a ramp (rising to a peak
  halfway through) and as a step (full strength throughout), lasting 14 days
  and starting at a random hour of the week after nine clean weeks.
- **Detected** means an alert while the outbreak is still going. **Time to
  detect** is hours from its start to the first alerting check.
- **False alarms** are alert episodes a week across all 100 series, over 52
  weeks with nothing injected.
- **Thresholds** 2, 2.5, 3 and 3.5 sd are scored on the same simulated counts.
- **Seeded.** The same seed always gives the same numbers; the README states
  the seed its figures came from.

## Consequences

- The numbers in the README can be regenerated by anyone in a minute, and the
  tables are printed as Markdown ready to paste.
- The measurement drove a real design change: it showed the rule as written
  raising ten false alarms a week, which led to the refinement in
  [ADR 0007](0007-detection-v1.md).
- The figures describe the detector against this simulator, not against real
  disease. Their limits are stated with them:
  - Series are independent, and baselines contain no past outbreaks. A real
    baseline inflated by last season's epidemic would lower sensitivity, which
    is the known recalibration weakness.
  - Every report arrives on time. Late returns would delay detection further.
  - Only counts are measured. Where patients live does not affect the z-score;
    the geographic check arrives in Phase 6 and will need its own measurement.
  - Throughput and end-to-end latency are properties of the pipeline, not the
    detector, and are measured when Kafka arrives in Phase 5.

## Alternatives considered

- **Measure through the full pipeline.** The most faithful, but days of run time
  for a few hundred outbreaks. It remains useful as a demonstration, and the
  README shows one injected outbreak raising one alert end to end.
- **A separate simulation inside the detector.** Faster to write, but two
  models of the same world drift apart, and the numbers would describe the copy.
